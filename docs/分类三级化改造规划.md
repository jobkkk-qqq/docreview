# 分类管理三级化改造规划

## 1. 需求确认

将现行"分类管理"扩展为三级分类结构：

| 层级 | 名称 | 数据来源 | 说明 |
|------|------|----------|------|
| 一级 | 分类 | 现有 `categories` 表 | 维持现状，用户可增删改 |
| 二级 | 部门分类 | `departments` 表（实时引用） | 以部门管理里的部门作为类别，部门增改自动反映 |
| 三级 | 文档级别 | 固定 5 级 | Ⅰ级文件 / Ⅱ级文件 / Ⅲ级文件 / Ⅳ级文件 / 无级别 |

**已确认的两个架构决策：**
- 数据承载：**Document 增加独立字段**（一级沿用现有 `category_id`；文档新增 `department_id`（二级）、`doc_level`（三级）），不把 `categories` 建成多层级树。
- 部门联动：**实时引用部门表**，不复制快照。

**数据迁移规则：** 升级后，存量文档的部门分类保留空白（`department_id = NULL`），文档级别默认为"无级别"（`doc_level = '无级别'`）。

## 2. 后端改动

### 2.1 文档模型 — `backend/app/models/document.py`
- 新增字段：
  - `department_id: Integer | None`，`ForeignKey("departments.id", ondelete="SET NULL")`，nullable，注释"所属部门(二级分类)"
  - `doc_level: String(20)`，`server_default="无级别"`，非空，注释"文档级别(三级分类)"
- 新增索引：`ix_documents_department_id`、`ix_documents_doc_level`
- 新增关系：`department -> Department`（`lazy="selectin"`），仅用于展示时内嵌部门名

### 2.2 文档级别常量 — 新增 `backend/app/core/doc_levels.py`
```python
DOC_LEVELS = ["Ⅰ级文件", "Ⅱ级文件", "Ⅲ级文件", "Ⅳ级文件", "无级别"]
```
供后端校验、接口返回、迁移默认值复用，避免硬编码散落。

### 2.3 文档 Schema — `backend/app/schemas/document.py`
- `DocumentCreate`：新增 `department_id: Optional[int]`、`doc_level: str = "无级别"`
- `DocumentUpdate`：新增 `department_id: Optional[int]`、`doc_level: Optional[str]`
- `DocumentOut` / `DocumentListOut`：新增 `department_id`、嵌套 `department: DepartmentBrief | None`、`doc_level`
- 新增 `DepartmentBrief{id, name}` 响应模型（与已有 `CategoryBrief` 写法一致）

### 2.4 数据库迁移 — `backend/app/core/auto_migrate.py`
- `CURRENT_SCHEMA_VERSION` 4 → **5**
- 新增 `_migrate_v5(conn)`：
  1. 检查 `documents` 有无 `department_id` 列，无则 `ALTER TABLE documents ADD COLUMN department_id INTEGER`
  2. 检查有无 `doc_level` 列，无则 `ALTER TABLE documents ADD COLUMN doc_level VARCHAR(20) DEFAULT '无级别'`
  3. 回填：`UPDATE documents SET doc_level='无级别' WHERE doc_level IS NULL OR doc_level=''`
  4. 创建 `department_id`、`doc_level` 索引（用 `CREATE INDEX IF NOT EXISTS`）
- 迁移保证幂等（先查列/索引是否存在再执行），不破坏现有数据。

### 2.5 部门 simple 接口 — `backend/app/api/department_router.py`
- 新增 `GET /api/departments/simple`：依赖 `get_current_user`（仅需登录即可访问），返回 `is_active` 部门的 `{id, name}` 列表，供上传、筛选时普通用户选择二级分类。

### 2.6 文档级别接口 — `backend/app/api/system_router.py`（或 category_router）
- 新增 `GET /api/system/doc-levels`：返回 `DOC_LEVELS` 5 级列表，保证前后端一致、便于将来改可配置。

### 2.7 文档接口 — `backend/app/api/document_router.py`
- 列表接口：新增 `department_id`、`doc_level` 查询参数过滤。
- 创建/更新（上传）接口：接收 `department_id`、`doc_level`；校验 `doc_level` 在 `DOC_LEVELS` 内；`department_id` 若提供则校验存在于 `departments` 且 `is_active`。
- 响应：将 `document.department` 内嵌返回（`selectinload(Department)`），确保不触发 MissingGreenlet。
- 权限说明：二级（部门）、三级（级别）**不参与权限校验**——文档可见性、下载/编辑权限仍按现有分类（一级）逻辑，本期不扩展权限维度。

## 3. 前端改动（Vue3 / Element Plus）

### 3.1 前端 API
- `frontend/src/api/department.js`：新增 `getDepartmentSimple()`
- `frontend/src/api/category.js` 或 `document.js`：新增 `getDocLevels()`
- `document.js`：列表/详情/上传请求参数中加入 `department_id`、`doc_level`

### 3.2 上传页 — `frontend/src/views/DocumentUpload.vue`
- 分类选择从单一"分类"改为**三级联动**：
  1. 一级分类：现有 `el-select`（数据源 `/categories/simple`，保留业务角色推荐逻辑）
  2. 部门：新增 `el-select`（数据源 `/departments/simple`，可留空）
  3. 文档级别：新增 `el-select`（数据源 `/system/doc-levels`，默认"无级别"）
- 单文件/批量上传的表单与 payload 增加 `department_id`、`doc_level`

### 3.3 文档管理页 — `frontend/src/views/DocumentManage.vue`
- 搜索栏新增"部门""文档级别"筛选下拉。
- 表格新增"部门""文档级别"列（Tag 展示）；列宽持久化 key（`column-key`）同步增加。

### 3.4 文档列表/详情展示
- 文档列表（`DocumentList` 等出现 `category`/分类名处）与详情页：展示"部门""文档级别"。

### 3.5 分类管理页 — `frontend/src/views/CategoryManage.vue`
- 该页展示全部三级信息，体现"分类管理三级化"：
  - 一级：现有分类管理表格（增删改，保持现状）
  - 二级：只读展示"部门"列表（数据源 `/departments/`，提示维护入口在"部门管理"）
  - 三级：只读展示 5 个文档级别（数据源 `/system/doc-levels`，提示为内置固定级别）

## 4. 数据迁移与验证

1. 升级启动后端 → `Base.metadata.create_all` → `auto_migrate` 执行 v5。
2. 验证日志：`docreview.log` 中出现添加列的 DDL、索引创建记录。
3. 抽样检查：存量文档 `department_id IS NULL`、`doc_level = '无级别'`。
4. 冒烟流程：
   - 上传新文档可选择 一级分类→部门→文档级别
   - 列表可按部门/文档级别筛选与展示
   - 分类管理页显示 3 级结构
   - 老版本客户端接口无回归（`/categories/simple` 等未破坏）

## 6. 风险与注意点
- 迁移必须幂等，避免重复启动时重复加列/索引。
- 文档响应内嵌 `department` 需 `selectinload` 预加载，避免异步懒加载异常（沿用项目既有约定）。
- 老文档无部门，前端需对 `department` 为空做容错展示。
- 不扩展三级权限校验（二级/三级仅作为归档维度），与现有权限体系解耦，降低回归风险。
